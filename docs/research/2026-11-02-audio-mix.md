# Audyt miksu audio: 13 nowych dźwięków CC0 (2026-11-02)

Zakres: `src/audio/sounds.ts` (36 id: 4 ambient, 2 wózki, 30 sfx/ui), `bindings.ts`, `audio.ts`,
pliki `public/assets/audio/**`. Nic w `src/` nie zostało zmienione. Narzędzia do powtórzenia:

- `python3 tools/audio-mix-audit.py > mix.json` (ffmpeg + numpy: LUFS/TP z ebur128, RMS aktywny,
  K-ważony, pasma, szwy pętli),
- `npx tsx tools/audio-trigger-sim.ts > triggers.json` (prawdziwy sim m8–m12 + sandbox 90 min,
  prawdziwy `observeSim`, atrapa silnika z cooldownem/promieniem jak w `AudioEngine.play`;
  `COOLDOWN=load.sack:0.8,...` podgląda poprawkę).

## Streszczenie

1. **Poziomy**: nowe dźwięki są w większości w normie, ale 4 odstają o > 3 LU od mediany swojej
   grupy: `work.charcoal` (-12 LU, za cichy), `work.quarryRock` (-5), `work.quarry` (-4),
   `unload.barrel` (+5,6, za głośny). `work.malt` ma najgorętszy szczyt w całej bibliotece (-2,8 dBTP)
   i jest +6,5 dB ponad medianą na głośniku telefonu. Z istniejących: `work.oven` (-6,6).
2. **Pętle**: żaden z 13 nowych nie jest pętlą (wszystkie one-shoty). Istniejące pętle są czyste,
   poza `ambient.evening` (skok poziomu 5,8 dB w paśmie basowym na szwie; brak kliku w słyszalnym
   paśmie na głośniku telefonu).
3. **Gęstość**: żaden id nie przekracza ~20/min na x1. Ryzyko spamu to tylko `load/unload.sack`
   (15 + 14 / min przy kamerze na zamku, 55/min na x4, cooldown 0,06 s nic nie ogranicza).
   Natomiast **nowe dźwięki pracy są prawie ciche**: grają tylko przy *wejściu* budynku w WORKING
   (raz na kilkadziesiąt sekund do kilku minut). Kamieniołom w m8 gra 2 razy w 9,5 min.
   Wszystkie 13 id odpala się przynajmniej raz w jakimś scenariuszu (nic nie jest "martwe").
   `(b.id + (tick>>6)) % 2` **naprawdę naprzemienia** (kamieniołom 12/12, rybak 17/20 i 16/14).
4. **Maskowanie stall.alert**: `ui/stall` to w 99,5 % energia poniżej 200 Hz (szczyt 42 Hz,
   centroid 88 Hz); w paśmie 1–4 kHz ma -59 dB, czyli 6–22 dB mniej niż każda praca/ambient.
   Pętle robocze go nie maskują, bo to inny region widma; problem leży gdzie indziej: na głośniku
   telefonu (filtr górnoprzepustowy ~300 Hz) alert spada do -50 dB, o 10–15 dB poniżej wszystkiego
   wokół. Gain tego nie naprawi; trzeba zregenerować asset z energią 600–2500 Hz. To samo dotyczy `ui.error`.

Wniosek o spamie: tylko worki. Cooldown 0,06 s (jeden tick to 0,1 s) w praktyce nie ogranicza niczego.
Podgląd poprawki (`COOLDOWN=...`, sandbox, x1 / x4 na load.sack): 0,06 s: 15,0 / 56,7; 0,5 s: 13,4 / 39,3;
**1,0 s: 12,0 / 29,2**; 1,5 s: 10,7 / 22,4. Zalecane 0,8 s (kompromis: x4 ok. 30/min).

Cisza ("podpięte, ale prawie nie gra"). Dźwięki pracy odpalają się w `observeSim` tylko przy przejściu
`!WORKING -> WORKING`. Zmierzone w sandboxie (90 min): budynki są w WORKING 65–95 % czasu,
a pojedynczy przebieg WORKING trwa średnio: tartak 37 s, drwal 64 s, piekarnia 95 s, rybak 76 s,
**kamieniołom 140 s, węglarz 184 s, piwowar 216 s**. Efekt: gdy zakład pracuje nieprzerwanie, jest
niemy; kamieniołom w m8 daje 2 dźwięki w 9,5 min. To znaczy, że "cisza" nie odróżnia budynku
pracującego od stojącego, a gracz uczy się diagnozować właśnie po odgłosach. Zalecenie dla
`bindings.ts` (poza zakresem tego audytu, snippet niżej): powtarzać akcent co N tików w trakcie
WORKING ze stałą fazą per budynek.

Naprzemienność `(b.id + (tick>>6)) % n`: działa. Z sandboxa: kamieniołom #341 24 starty, 12 wariantów
0 / 12 wariantów 1, 11 przełączeń; rybak #339: 17/20 (18 przełączeń), rybak #458: 16/14 (16).
Uwaga: ponieważ `tick>>6` zmienia się co 6,4 s, a przebiegi WORKING trwają dziesiątki sekund,
naprzemienność jest losowa-pseudolosowa, nie ściśle ABAB (m8: kamieniołom 2 starty = 1+1).
Nie ma wzorca "zawsze ten sam" (nie ma dzielnika 64 w długości cyklu).

Inne obserwacje z `audio.ts`:
- `getBuffer` ładuje bufory **leniwie przy pierwszym `play`**; jeśli fetch+decode zajmie > 850 ms,
  pierwszy dźwięk jest po cichu gubiony (`requestedAt` w `play`). Rzadkie id (brewery 0,0/min,
  kamieniołom, ładunki ryby/kamienia) mogą więc milczeć dłużej niż wynika z gęstości. Całość sfx+ui
  to 307 kB (ogg), więc wstępne ładowanie wszystkich jednorazowych po `init()` jest tanie.
- `load.stone` ma 55 ms ciszy na początku pliku (opóźnia uderzenie względem animacji). Przyciąć.

## 4. Maskowanie `stall.alert`

Energia pasmowa po zastosowaniu gainu (dB re FS², to samo okno aktywne):

| źródło | 40–125 Hz | 125–250 Hz | 1–4 kHz |
|---|---|---|---|
| **stall.alert** | -32,5 | -49,4 | **-59,0** |
| work.* nowe: malt / brewery / charcoal | -51 / -63 / -51 | -40 / -35 / -51 | -48 / -56 / -60 |
| work.quarry / quarryRock | -54 / -90 | -53 / -75 | -50 / -43 |
| work.fisher / fisherSplash | -56 / -59 | -44 / -53 | -39 / -39 |
| unload.barrel / load.fish / load.stone | -61 / -50 / -91 | -32 / -41 / -76 | -47 / -38 / -40 |
| ambient.evening | -35,5 | -46,4 | -46,4 |
| cart.dirt / cart.cobble | -38,0 / -37,9 | -45,5 / -49,4 | -50,1 / -53,0 |

- 1–4 kHz: alert ma tu praktycznie zero energii (0,1 %). Nowych pętli roboczych nie ma;
  nowe jednorazowe dźwięki pracy w 1–4 kHz leżą -38 … -60 dB, czyli 0–21 dB ponad alertem
  w tym paśmie. Ale alert nie żyje w 1–4 kHz, więc to nie jest maskowanie wprost.
- Pasmo alertu to 40–125 Hz (-32,5 dB). Konkurenci w tym paśmie: ambient.evening (-35,5),
  cart.dirt/cobble (-38), worki (-36 … -39), `load.log`/`bridge.wood` (-33/-34). Nowe jednorazowe
  dźwięki są tam znacznie cichsze (<= -50). Zapas alertu nad pętlami to tylko 3–6 dB,
  nad `ambient.evening` 3 dB. Nowe dźwięki pracy zasłaniają go jedynie w 125–250 Hz (brewery,
  malt, unload.barrel o 10–18 dB), ale to krótkie jednorazowe zdarzenia (< 4 s, rzadkie).
- Na głośniku telefonu (HP 300 Hz): alert -50,4 dB, `ui.error` -50,9, przy medianie pracy -39,
  a pętle wózków -41 … -46. Gracz na telefonie dostaje alert o 10–15 dB cichszy od otoczenia.
  Gain 0,38 -> 0,55 (+3,2 dB) to tylko tymczasowa łata dla słuchawek; właściwa naprawa to nowy
  render `stall` w `tools/generate_audio.py` (gałąź `kind == 'stall'`): dodać dwutonowy akcent
  ok. 700–1400 Hz o czasie 0,15–0,3 s przy zachowaniu basu, tak by 1–4 kHz było tylko 6–10 dB pod
  pasmem pracy. Ten sam problem ma `ui.error` (99,5 % energii < 100 Hz).

w pipeline. `ui.paper` (+5,9 LU) i `unload.sack` (-3,6) świadomie nie ruszane. `unload.stone` bez zmian.

### Szkic zmiany w `bindings.ts` (nie część patcha gainów)

Cel: slyszalna praca w trakcie WORKING (akcent co ~25 s, faza stała per budynek), niezależnie od
istniejącego startu:

```ts
// inside the building loop, after the onset branch
const REPEAT = 25 * TICK_HZ;
if (b.status.k === 'WORKING' && old?.status === 'WORKING' && ids &&
    (state.tick + b.id * 37) % REPEAT === 0) {
  play(ids[(b.id + (state.tick >> 6)) % ids.length]!, p);
}
```

Przy 25 s i ~10 budynkach w zasięgu to nadal < 25/min łącznie, ale każdy cooldown id (0,2–0,3 s)
musi przetrwać zbieżność faz; do sprawdzenia przy użyciu `tools/audio-trigger-sim.ts`.
Powinno też dojść wstępne ładowanie buforów po `init()`.
